엔드포인트의 4가지 핵심 (4 Things to Get Right)
1
THE ENDPOINT — one door, one job
One clear address that does one job. Skip it: one messy entrance, hard to secure
2
AUTH — who can call it?
Confirm identity, then access ownership. Skip it: users can read each other's private data
3
VALIDATION — what data? right shape?
Inspects the input, rejects junk + bad values. Skip it: garbage data corrupts or crashes the app
4
RATE LIMIT — stop abuse
Drop requests, blocks bots & abuse. Skip it: one bot finds you and runs up your bill

🏪 비유로 이해하기

데이터베이스는 대형 창고라고 생각하세요. 창고 안에는 선반(테이블)이 있고, 각 선반에는 상자(행, row)들이 쌓여 있어요. 그런데 이 창고는 아무나 들어오면 안 되겠죠? 창고 열쇠(권한)를 가진 사람만 들어올 수 있고, 들어오더라도 자기 상자만 열 수 있어야 해요 — 그게 바로 RLS입니다.

⚠️ RLS(행 보안) — 켜야 하는데 AI는 안 켬
❌ RLS 꺼진 상태 — 데이터 유출
  • AI가 코드를 짜면 기본값이 꺼진 상태
  • 누구든(해커도) 모든 사람의 데이터를 볼 수 있음
  • 내 개인정보가 남에게 그대로 노출
✅ RLS 켜진 상태 — 안전
  • 데이터베이스가 자동으로 필터링해 줌
  • 각 사용자는 자기 데이터만 볼 수 있음
  • 다른 사람 데이터는 완전히 숨겨짐
  • 해커가 접근해도 빈 결과만 나옴
⚠️ RLS는 기본으로 꺼져 있습니다. 켜지 않으면 모든 사용자의 데이터가 서로 노출됩니다. 웹 보안 1위 위험 항목(OWASP)이며, AI가 만든 앱의 70%가 이 설정을 놓쳐 출시되었습니다. Supabase를 쓴다면 반드시 직접 RLS 켜기!

AI와 개발하는 건 요리사 여러 명이 주방에서 동시에 요리하는 것과 같아요. 한 명은 메인 요리, 한 명은 디저트, 한 명은 스프. 그런데 서로 방해하면 안 되겠죠? Git Worktrees는 각 요리사에게 별도의 조리대를 주는 것입니다. 동시에 진행하고, 완성된 것만 테이블에 올려요.

❌ 기존 방식 — 번갈아가며 작업
  • 기능 작업 중 → 임시 저장(stash)
  • 긴급 수정으로 전환
  • 긴급 수정 완료
  • 다시 기능 작업으로 복귀
  • 임시 저장 꺼내기 (충돌 발생?)
✅ Worktrees — 동시에 작업
  • 기능 작업: 멈추지 않고 계속
  • 긴급 수정: 별도 폴더에서 병렬 진행
  • 코드 검토: 또 다른 폴더에서 확인
  • 각자 독립 — 서로 방해 없음

🔍 SEO vs AEO — 두 채널의 차이
📡 비유로 이해하기

SEO는 구글 검색 결과 1페이지에 내 간판 세우기. 사람들이 직접 클릭해서 옴. AEO는 ChatGPT나 Perplexity가 답변할 때 내 앱을 인용하게 만들기. 링크 클릭 없이도 이름이 알려짐. 둘 다 하면 광고비 없이 자는 동안에도 노출됩니다.

SEO — 구글 검색 최적화
  • 내 페이지가 검색 결과에 상위 노출
  • 링크 형태로 구글·빙에 표시
  • 사용자가 클릭해서 방문
  • 제목·내용·링크 최적화 필요
  • 구글, 빙에서 효과적
AEO — AI 답변 최적화
  • AI가 질문에 답할 때 내 앱 인용
  • AI 답변 안에 출처로 표시
  • 클릭 없이도 이름 알려짐
  • 권위·신뢰성 있는 데이터 필요
  • ChatGPT, Perplexity에서 효과적
💡 AEO는 SEO를 확장한 것 — 대체가 아닌 추가입니다.
한 번 올리면 계속 노출. 광고비 제로.

웹훅은 택배 배송 알림 같은 거예요. 택배가 오면 알림이 와서 내가 찾아가는 게 아니라 — 고객이 결제하는 순간 Stripe가 내 앱에 자동으로 "결제 완료!" 신호를 보내줍니다. 내 앱은 그 신호를 받고 이용권을 열어줘요. 폴링(Polling)은 내가 계속 전화해서 "결제됐어요?" 묻는 것, 웹훅은 상대방이 알아서 전화해 주는 것입니다.

🤖 LLM — 12살도 이해하는 작동 원리
📚 비유로 이해하기

LLM은 수천억 개의 책과 글을 읽은 다음 "다음에 올 단어가 뭘까?"를 예측하는 기계예요. "오늘 날씨가___" 라고 주면 "좋네요"가 올 확률이 높다는 것을 학습으로 알고 있어요. 환각(Hallucination)이 생기는 이유도 이 때문 — 가장 그럴듯한 단어를 예측하다 보면 틀린 내용도 자신있게 써버립니다.

핵심
토큰 = AI의 기본 처리 단위
"안녕하세요"는 약 3~4 토큰. 입력+출력 토큰 수로 비용 청구. 긴 문서 = 많은 비용
핵심
컨텍스트 창 = AI의 단기 기억
Claude Sonnet은 약 20만 토큰. 이 범위 밖 내용은 AI가 "기억"하지 못함
핵심
Temperature = 창의성 조절 다이얼
0 = 매우 정확하고 반복적 / 1 = 창의적이지만 예측 불가. 코드 생성엔 낮게, 글쓰기엔 높게

2 Anthropic Console(console.anthropic.com)에서 API 토큰 계산기로 내 문장 토큰 수 확인하기 10분
3 Claude vs ChatGPT에게 같은 전문 질문 해보고 답변 품질 직접 비교하기 20분

✏️ 프롬프트 = AI에게 보내는 세밀한 주문서
📝 비유로 이해하기

음식점 주문을 생각해봐요. "뭔가 맛있는 거"(제로샷 — 막연함) vs "이전에 먹었던 김치찌개처럼 매운 국물 요리"(퓨샷 — 예시 제공). 주문이 구체적일수록 원하는 결과가 나와요. CoT는 "한 번에 답 말고, 과정을 하나씩 적어줘"라는 주문 — 복잡한 추론에서 정확도가 확 올라갑니다.

❌ 막연한 프롬프트
  • "마케팅 문구 써줘"
  • 역할·형식·길이 미지정
  • 결과: 너무 일반적인 답변
  • 반복 수정에 시간 낭비
✅ 구체적인 프롬프트
  • 역할: "당신은 SaaS 마케터"
  • 형식: "JSON으로 3개 제안"
  • 맥락: "B2B, 30대 대상"
  • 결과: 바로 쓸 수 있는 출력

🗂️ 벡터 DB — 음악 분위기 추천 비유
🎵 비유로 이해하기

일반 DB는 "제목이 '사랑'인 노래 찾기" 같은 키워드 검색이에요. 벡터 DB는 "이 노래와 비슷한 분위기의 노래 찾기"예요. 노래를 숫자(벡터)로 표현해서 "거리가 가까운" 것을 찾아줘요. 텍스트도 마찬가지 — "강아지가 아파요"와 "반려견 건강 문제"는 단어는 달라도 벡터상으로 가까워서 같이 검색됩니다.

⚙️ AI 에이전트 — "사장이 직원에게 지시" 비유
🏢 비유로 이해하기

기존 AI = 질문하면 답하는 백과사전. 에이전트 = 실제로 일을 하는 직원. "경쟁사 3곳 조사해서 보고서 써줘"라고 하면, 직원(에이전트)은 검색도 하고, 정리도 하고, 초안도 쓰고, 스스로 판단해서 완성본을 가져다줘요. 중간에 막히면 새 방법을 시도하고, 목표 달성하면 멈춥니다.

❌ 기존 AI (질답 방식)
  • 한 번 질문 → 한 번 답변
  • 다음 단계는 사람이 직접 해야 함
  • 도구 사용 불가 (검색, 실행 등)
  • 사람이 계속 개입 필요
✅ AI 에이전트 방식
  • 목표 하나 주면 스스로 계획
  • 도구 실행 → 결과 확인 → 반복
  • 막히면 다른 방법 시도
  • 완료되면 결과 전달 후 종료

예전엔 기기마다 충전 단자가 달랐죠 (마이크로USB, 라이트닝…). MCP는 AI 도구 연결의 USB-C 같은 통일 규격이에요. MCP 규격만 맞추면 GitHub, Slack, DB, 웹 검색 등 어떤 도구든 AI 에이전트에 바로 연결됩니다. Anthropic이 만든 표준이라 Claude에서 가장 자연스럽게 작동해요.

1단계
기존 MCP 서버 연결 (가장 쉬움)
claude_desktop_config.json에 MCP 서버 주소 추가. GitHub, 파일시스템 등 이미 만들어진 서버 연결
2단계
커스텀 MCP 서버 만들기
내 API나 DB를 AI가 접근할 수 있는 MCP 서버로 만들기. Python SDK로 가능
⚠️ 주의
MCP 보안 — 권한 반드시 확인
AI가 파일 삭제·이메일 발송 권한을 가질 수 있음. 필요한 최소 권한만 줘야 함
🎯 지금 바로 실습해보기
1 Claude Desktop 설치하고 파일시스템 MCP 서버 연결해보기 (공식 문서 따라하기) 30분
2 GitHub MCP 서버 연결해서 Claude가 내 저장소를 읽게 해보기 20분
3 Anthropic MCP 문서(docs.anthropic.com/en/docs/mcp)에서 MCP 서버 목록 구경하기 15분

📊 LLMOps — 실제 서비스에서 AI 관리하기
🏭 비유로 이해하기

AI 앱 만들기는 공장 세우기예요. 공장이 완성된다고 끝이 아니에요 — 매일 운영하면서 비용이 얼마 나오는지, 불량품(나쁜 답변)이 얼마나 나오는지, 기계(모델)가 멈추진 않는지 관리해야 해요. LLMOps는 그 관리 시스템입니다. 초기엔 단순하게 시작하고 사용자가 늘면 자동화하는 방향으로 가면 됩니다.

❌ 관리 없이 운영
  • 월말에 청구서 보고 깜짝
  • AI가 이상한 답 줘도 모름
  • 어느 프롬프트가 문제인지 불명확
  • 사용자 불만이 쌓인 후에야 발견
✅ LLMOps 적용
  • 일일 토큰 사용량 모니터링
  • 답변 품질 자동 평가
  • 문제 프롬프트 즉시 파악
  • 비용 초과 알림 설정
💡 비용 절약 팁: Anthropic의 프롬프트 캐싱(Prompt Caching)을 켜면 반복되는 시스템 프롬프트 처리 비용을 최대 90% 절감할 수 있어요. Claude API 사용 시 cache_control 파라미터를 추가하면 됩니다.
🎯 지금 바로 실습해보기
1 Anthropic Console(console.anthropic.com)에서 API 사용량 대시보드 구경하기 10분
2 내 앱의 AI 답변을 1~5점으로 평가하는 간단한 기준표 직접 만들어보기 20분
3 같은 기능을 Claude Haiku vs Sonnet으로 테스트해보고 품질·비용 차이 비교하기 20분
🎯 마일스톤 미션 AI심화 탭 최종 프로젝트
Claude API를 연결해서 나만의 AI 기능 한 가지 완성하기
예시: 글 요약기 / 아이디어 생성기 / 맞춤법 교정기 / 상품 설명 생성기
도구: Claude API (Anthropic) + Cursor + Vercel
성공 기준: 텍스트를 입력하면 AI가 응답하는 화면이 실제 URL로 배포되면 완성

🔍 사용자 리서치 — "지도 없이 여행 계획 짜지 않기"
🗺️ 비유로 이해하기

앱을 만들기 전에 리서치를 하지 않는 건 목적지도 모르고 길을 떠나는 것이에요. 내가 생각하는 "사용자가 원하는 것"과 실제 사용자가 원하는 것은 거의 항상 달라요. 인터뷰 5명이면 충분 — "왜 그렇게 생각하세요?"를 3번 연속으로 물어보면 진짜 니즈가 나옵니다.

1단계
가정 먼저 적기
"우리 사용자는 이런 사람이다"를 먼저 써보기. 리서치는 이 가정을 검증하는 과정
2단계
5명 인터뷰
30분씩, 과거 행동에 대해 물어보기. "이 기능 쓰실 건가요?" 금지. "요즘 어떻게 하세요?" OK
3단계
패턴 찾기
5명 중 3명 이상이 같은 말을 하면 진짜 문제. 그것을 먼저 해결하기
🎯 지금 바로 실습해보기
1 내 앱의 타겟 사용자 페르소나 1명 만들기 (이름·나이·직업·하루 루틴·고민 포함) 20분
2 주변 지인 1명에게 "요즘 [문제 상황]을 어떻게 해결하세요?" 30분 인터뷰하기 30분
3 내 앱의 사용자 여정을 포스트잇으로 단계별로 적어서 빈 칸(불편함) 찾기 20분

🎨 시각 디자인 — "첫인상은 0.05초에 결정된다"
👔 비유로 이해하기

앱 디자인은 첫 만남의 옷차림이에요. 내용이 아무리 좋아도 디자인이 허술하면 "이거 믿을 수 있나?" 의심부터 생겨요. 반대로 디자인이 깔끔하면 실제 기능보다 더 좋아 보여요. 60-30-10 법칙은 간단해요 — 배경 60%, 보조 색 30%, 포인트 색 10%. 이것만 지켜도 색상이 균형 있어 보입니다.

60%
배경 색 — 눈이 쉬는 공간
흰색, 연회색, 아주 연한 색. 화면의 대부분을 차지. 너무 화려하면 피곤함
30%
보조 색 — 구조를 잡는 색
사이드바, 카드 배경, 구분선 등. 배경과 구별되지만 튀지 않는 색
10%
포인트 색 — 행동을 유도하는 색
CTA 버튼, 링크, 강조 텍스트. 10%만 써야 눈에 띔. 너무 많이 쓰면 효과 없음
🎯 지금 바로 실습해보기
1 내 앱의 브랜드 컬러 팔레트 만들기 — coolors.co에서 3가지 색 조합 골라보기 20분
2 Google Fonts에서 제목용 + 본문용 글꼴 조합 2개 골라서 나란히 비교해보기 15분
3 좋아하는 앱 화면 스크린샷 찍고 60-30-10 법칙이 어떻게 적용됐는지 분석해보기 15분

💡 전환율 UX — "계산된 설득"
🛒 비유로 이해하기

편의점은 계산대 앞에 껌과 초콜릿을 놓아요 — 기다리는 동안 충동구매를 유도하는 설계예요. 웹도 마찬가지. 사용자가 머뭇거리는 순간마다 "지금 해야 해"를 느끼게 하는 UX 설계가 전환율을 올려요. 이건 속임수가 아니라 — 좋은 제품을 사람들이 더 쉽게 발견하고 결정하도록 돕는 것입니다.

❌ 전환율 낮은 UX
  • "가입하기" 버튼 (회색, 작게)
  • 회원가입 폼 12개 칸
  • 신용카드 먼저 입력 요구
  • 가격 표시 없이 "문의 주세요"
✅ 전환율 높은 UX
  • "14일 무료로 시작하기" (큰 버튼)
  • 이메일 하나로 즉시 가입
  • 카드 없이 무료 체험
  • 명확한 가격표 + 가장 인기 배지
🎯 지금 바로 실습해보기
1 내 앱 회원가입 단계를 세어보고 3단계 이하로 줄일 방법 찾아보기 15분
2 CTA 버튼 문구를 "시작하기" vs "지금 무료로 시작하기" 두 버전으로 테스트해보기 20분
3 Microsoft Clarity 무료로 설치하고 사용자가 어디서 멈추는지 히트맵 확인하기 30분

🚀 SEO × UX — "구글은 사용자 편에 서 있다"
🔎 비유로 이해하기

구글의 목표는 검색한 사람이 만족하게 하는 것이에요. 그래서 사람이 좋아하는 사이트 = 구글이 높이 평가하는 사이트예요. 빠르게 로딩되고, 모바일에서 잘 보이고, 사용자가 오래 머무는 사이트를 구글은 "좋은 사이트"로 판단해요. SEO를 위해 UX를 개선하면 — 사용자도 좋고, 검색 순위도 올라갑니다.

LCP
Largest Contentful Paint — 가장 큰 요소 로딩 속도
목표: 2.5초 이내. 이미지 최적화 + 서버 응답 속도가 핵심. 느리면 순위 하락
CLS
Cumulative Layout Shift — 화면이 갑자기 움직이는 정도
이미지에 width/height 지정 + 광고 공간 미리 잡기. 글 읽다가 화면 튀면 최악
INP
Interaction to Next Paint — 클릭 후 반응 속도
목표: 200ms 이내. 버튼 클릭했는데 반응이 없으면 사람도 구글도 싫어함
💡 즉시 확인하는 법: Google PageSpeed Insights (pagespeed.web.dev)에 내 사이트 URL 입력하면 Core Web Vitals 점수와 개선 방법이 바로 나옵니다. 무료.
🎯 지금 바로 실습해보기
1 pagespeed.web.dev에서 내 사이트(또는 경쟁사 사이트) Core Web Vitals 점수 확인하기 10분
2 내 랜딩페이지 HTML에서 h1 태그가 하나인지, 이미지에 alt 텍스트가 있는지 확인하기 15분
3 squoosh.app에서 이미지 하나를 WebP로 변환하고 파일 크기가 얼마나 줄었는지 확인하기 10분

🍳 비유로 이해하기

AI한테 "파란 버튼 만들어줘"라고 하면 매번 다른 파란색, 다른 크기가 나와요. 하지만 "#3b82f6 색상, 8px 모서리, 14px 폰트, 위아래 여백 12px 버튼"이라고 하면 — 오늘도 내일도 같은 버튼이 나옵니다. 이 규칙 모음이 바로 Design Tokens이고, CLAUDE.md 파일에 적어두면 AI가 매 대화에서 자동으로 참고해요.

📋 CLAUDE.md 디자인 규칙 예시
# Design Tokens — 이 파일을 프로젝트마다 만들어두세요 Colors: primary: #3b82f6 # 버튼, 링크, 강조 neutral: #94a3b8 # 보조 텍스트 danger: #f43f5e # 에러, 삭제 bg: #0a0a12 # 배경 Spacing: 4 · 8 · 12 · 16 · 24 · 32px # 8px 배수만 사용 Radius: 6 · 8 · 12 · 16px Font: 12 · 14 · 16 · 20 · 24px Components: Button: ShadCN 기반, primary color, 8px radius, 14px font Card: bg2 배경, 1px border(#2d2d4a), 12px radius, 16px padding
